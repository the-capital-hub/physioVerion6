# Rehabics V6 Patient Panel — Alpine Horizon

A responsive patient portal module for a React + Vite app. It preserves the app's shared Navbar/Footer because this module intentionally renders neither. It includes Overview, Appointments, Exercise Plan, Recovery Progress, My Physiotherapist, and Profile routes.

## Files

- `src/pages/PatientPanel/PatientPanel.jsx`
- `src/pages/PatientPanel/PatientPanel.css`
- `src/services/patientApi.js`

## 1. Install dependencies

From your existing project root:

```bash
npm install axios lucide-react react-router-dom
```

If `react-router-dom` and `axios` are already installed, you do not need to reinstall them.

## 2. Copy the files

Copy the `src/pages/PatientPanel` folder into your project's `src/pages/` directory and copy `src/services/patientApi.js` into your project's `src/services/` directory. If you already have an API service, merge the endpoint configuration and token logic instead of overwriting your existing service.

## 3. Configure the API base URL

Add this to `.env` in the project root (use your actual API URL):

```env
VITE_API_BASE_URL=http://localhost:5000/api
```

Restart Vite after changing `.env`.

## 4. Add the routes

Import the module in your existing `App.jsx`:

```jsx
import PatientPanel from "./pages/PatientPanel/PatientPanel";
```

Add this route inside the existing router, while preserving your existing Navbar/Footer and other routes:

```jsx
<Route path="/patient/*" element={<PatientPanel />} />
```

Do not put another global Navbar or Footer inside `PatientPanel.jsx`. If your existing layout renders shared Navbar/Footer around all routes, keep that layout as it is. If your shared layout should not appear inside authenticated dashboards, use your existing layout/route-group pattern to exclude it rather than duplicating components.

## 5. Connect your actual API routes

Open `src/services/patientApi.js` and change `patientEndpoints` to match your backend. The default routes are examples only:

```js
export const patientEndpoints = {
  me: "/patient/me",
  appointments: "/patient/appointments",
  exercises: "/patient/exercises",
  progress: "/patient/progress",
  therapist: "/patient/therapist",
  profile: "/patient/profile",
};
```

The request interceptor looks for a token under `token`, `accessToken`, or `authToken` in `localStorage` and sends `Authorization: Bearer <token>`. If your existing auth stores the token elsewhere, update `getAuthToken()` to use your current auth service/context. Never create a second login flow if the current login already works.

### Expected response shapes

The UI accepts an object or `{ data: object }` for profile/progress/therapist, and an array or `{ data: array }`, `{ items: array }`, or `{ results: array }` for list resources. Adapt field names in the UI or normalize them in the API service if your API uses a different schema.

Typical fields used:

- Profile: `name` or `fullName`, `email`, `phone`, `condition` or `primaryCondition`
- Appointment: `_id`/`id`, `type`/`title`, `date`/`startTime`/`appointmentDate`, `status`, `therapistName` or nested `therapist.name`, `mode`
- Exercise: `_id`/`id`, `name`/`title`, `description`/`instructions`, `sets`, `reps`/`repetitions`, `completed`/`isCompleted`
- Progress: `recoveryPercent`, `completedSessions`, `totalSessions`, `weeklyActivity: [{ label, value }]`
- Therapist: `name`/`fullName`, `specialty`/`specialization`, `experience`, `email`, `phone`, `availability`

## 6. Important security notes

- The frontend route is not a security boundary. Every backend endpoint must authenticate the token and verify the patient is only accessing their own record.
- Do not trust a patient ID supplied in query/body parameters without checking it against the authenticated user on the server.
- The sample fallback values are illustrative only. Remove `demoData` and the fallback behavior for production, so unavailable patient data is not mistaken for real clinical information.
- Profile save uses `PATCH /patient/profile`; exercise completion uses `PATCH /patient/exercises/:id/completion`. Change these requests to your backend's actual contract.
- Appointment request uses an email link only; it does not create a booking in the backend. Connect it to your booking endpoint if you want live booking.
- No medical diagnosis or treatment advice is generated by this panel.

## 7. Theme and integration

Alpine Horizon tokens are scoped to `.rp-shell`: Indigo `#6366F1`, Ice Cyan `#22D3EE`, Emerald `#10B981`, Cloud `#F8FAFC`, dark background `#10131B`, dark surface `#191E29`, and Plus Jakarta Sans. The panel has its own light/dark toggle and responsive sidebar. It does not modify existing app routing except for the route you add.

## 8. Test

1. Start your backend and frontend.
2. Sign in using your existing login as a patient.
3. Visit `/patient`.
4. Inspect the browser Network tab. If requests return 404, update the endpoint map. If requests return 401, connect `getAuthToken()` to the token used by your current login. If requests return 403, verify the backend patient-role authorization.
5. Test profile saving and exercise completion only after confirming the matching PATCH endpoints exist.
